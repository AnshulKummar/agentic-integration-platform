The problem

Integration is the bottleneck of SaaS product management

Traditional integration is code-centric: every hand-off translates the need again, and each translation adds delay and loses information.

Business need"New signed customers should flow into finance."
→
Technical specFields, endpoints, authlatency · information loss
→
CodeGlue code per vendor pairlatency · information loss
→
Integrate & testAgainst real use casesrework when APIs change

Brittleness amplification

Each integration point adds dependencies that multiply across the system, so the burden grows faster than the number of integrations.

The business cost

PMs and skilled engineers spend their time on connectivity instead of customers: delayed customization, stalled sales cycles, mounting technical debt.

Why now

Three technologies make a different approach viable

LLMs

Understand intent

Read natural-language requirements and API docs; plan, generate and test integration code.

Knowledge graphs

Encode business meaning

Semantic relationships between systems, objects and processes; GraphRAG grounds LLM reasoning in them.

Model Context Protocol

Standard tool access

Plug-and-play agent access to APIs, with context carried across sessions. REST APIs can be wrapped as MCP tools automatically.

Thousands of MCP servers were deployed by 2025, and enterprise-grade agentic frameworks matured, which makes multiagent integration practical at scale.

The core idea

From code-centric to intent-centric development

End users, PMs and technical teams describe the business outcome in their own words. Agents interpret, plan, generate, test and deploy.

"When a new sales prospect signs the deal, create a contract using a document signing application, and send the prospect data to our finance system once the customer has completed the agreement."

Semantic compression

No translation through technical intermediaries. Requirements stay in the business's native vocabulary.

Parallel agents

Multiple agent instances work on different parts of the request at the same time (Fig. 1), instead of a sequential hand-off chain.

System architecture

PMAIP: three agent types that collaborate

LLM agent

Interprets & generates

  • Clarifies intent, source and target systems
  • Synthesizes context into an integration plan
  • Generates integration code
KG agent

Remembers & grounds

  • Prior integrations, schema mappings, patterns
  • Semantic equivalence across systems
  • Institutional memory, updated after each integration
MCP agent

Connects & deploys

  • Tests API connectivity
  • Deploys and tests against live endpoints
  • Standard interfaces, no per-tool plumbing

Workflow: (1) accept intent and start a conversation → (2) query the KG with the conversation and history → (3) generate and test code → (4) return results with options to refine.

The knowledge graph

Semantic grounding and institutional memory

Same entity, different systems

A CRM Account and an ERP Customer are the same business entity, despite different field names, types and validation rules.

Business processes, not just fields

Encodes how entities take part in processes: order status, payment terms, fulfillment. Generated code handles the workflow, not only the data mapping.

Institutional memory

It tracks customer needs, interoperability patterns and field-specific handling, and is updated after every integration for the next one.

In a company, that means…

  • "Our ERP wants the legal company name"
  • "Never sync the sales rep; the ERP assigns it"
  • "UDF_07 is our sales region"

Findings (observational)

Integration capability moves closer to the business

1–4 wks → 1–4 days
Observed interaction cycle, conventional vs agentic integration, so several intent options can be tried in parallel

Task reallocation

Business users prototype integrations directly instead of queuing for engineering. New hybrid roles appear: PMs and end users grow skills in data modeling and workflow design.

Integration governance

Empowerment needs controls: decision rights, quality standards and approval processes for business-user-generated integrations.

Based on the authors' experience and conversations with product managers (a convenience sample).

Beyond the paper's prototype

We built it as a multi-tenant platform, then measured it

Trust & access

  • Login, roles, dual approval
  • Per-company isolation (incl. row-level security)
  • Encrypted vendor credentials

Safe execution

  • Generated code runs in a sandbox with no network or secrets
  • Connectors generated from OpenAPI
  • Audit trail

Safe delivery

  • Staged deploys with real health checks
  • Automatic rollback on a vendor outage
  • Metrics, alerts, dashboards

The paper's limitations section asks for "methods for measuring the compound advantage." So we built an evaluation suite: 72 generated cases, 19 hand-labeled realistic cases, and a pre-registered company-conventions experiment.

Repo: app/platform · app/platform/evals14

Evidence 1 · realistic hand-labeled cases

The LLM agent removes almost all mapping work

18.5% → 97.1%
Fields mapped correctly (F1): classic name matching → Claude agent
12.1 → 0.5
Human corrections per integration: about 23× fewer

Trustworthy confidence

Every mapping the agent rated ≥ 0.8 confidence was correct, so reviewers can focus on the few low-confidence ones.

But: the KG adds nothing here

On fields whose meaning is public knowledge, KG on vs off showed no measurable difference. There was nothing left to fix.

Honest limits

Limitations and next steps

Limitations

  • Paper findings: a simplified use case and a convenience sample
  • Evals: one model, one labeler; synthetic, perfectly consistent conventions; real companies have exceptions and drift
  • Vendors are simulators; no real customer data yet
  • Claude + KG context is measured in the evals, not yet wired into the platform's drafting

Next steps

  • Run the conventions test on a real company's integration history
  • Wire Claude + KG context into drafting; add an approvals UI
  • Longitudinal study of organizational effects and governance (paper's future work)
  • Connect real vendor sandboxes
